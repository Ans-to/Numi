# Security design and limits

## Threat model

Intended protection: someone casually using the calculator, another unprivileged Android app, a copied encrypted file, accidental task previews/screenshots, malformed media, and incomplete imports. Android app sandboxing and Android Keystore are part of the trusted computing base. The app does not claim protection against a rooted device, OS compromise, hooking/debugging, malicious accessibility services/keyboards, forensic access to live process memory, or an attacker with the device already unlocked into the vault.

**Production release gate:** complete the Android build/device matrix and obtain an independent security review before relying on the app for irreplaceable sensitive material. Implementing cryptography does not by itself establish production security.

## Key hierarchy and authentication

- The root AES-256-GCM key is generated by `AndroidKeyStore`. It is non-exportable through the public Android API; hardware backing depends on the device. No claim of universal hardware isolation is made.
- The root key encrypts `auth` and `catalog` independently, with fresh provider-generated 96-bit IVs, 128-bit authentication tags, and the record name as associated data. Files reside under `noBackupFilesDir/security`.
- Each import gets an independent cryptographically random AES-256 content key. Content keys, names, MIME types, size, digest, date and folders are in the root-encrypted catalog; none are used as public filenames.
- The PIN is an **application access gate**, not a second independent key-encryption factor. Only a PBKDF2-HMAC-SHA256 verifier (256-bit output, 256-bit random salt, 600,000 iterations) is stored, inside the encrypted auth record. Comparisons are constant-time. A PIN change updates the verifier and does not re-encrypt media.
- The first four PIN-length attempts reserve at least one second; subsequent attempts progressively delay up to five minutes. The reservation is atomically persisted **before** deriving/verifying the input. A clock rollback fails closed until the persisted time is reached. This local wall-clock policy is not a tamper-proof hardware rate limiter; changing the clock forward can affect delays. It is not a defense against privileged rollback of app data or an attacker able to invoke the app's Keystore key directly.
- A separate biometric AES key requires strong biometric authentication on every operation. Enrollment performs a CryptoObject encryption; unlock requires authenticated decryption of the saved challenge. Enrollment changes invalidate the key. No `onAuthenticationSucceeded` event alone opens storage; cryptographic verification must succeed. Any strong biometric identity enrolled on the device can approve the prompt; Android does not identify a particular owner fingerprint to the app. A PIN fallback is always available, but Android device credentials are not implicitly treated as the vault PIN.
- The OS does not cryptographically enforce the app's numeric PIN. The root key is not tied to the biometric key because PIN-only use must remain supported. A modified app/process can bypass this application-level gate; release signing and the Android sandbox matter.

## Chunked authenticated file format (version 1)

Ciphertext file counts and lengths are not padded or hidden; someone with access to the encrypted directory can infer these even without decrypting the catalog. This is encryption, not filesystem steganography.

All integers are big endian. Each ciphertext file is named `<UUID>.cv`, independent of the source name, under `noBackupFilesDir/vault`.

```text
Header: "CVCHNK01" (8 bytes) | chunk size 1048576 (4 bytes) | random nonce prefix (8 bytes)
Record: plaintext length (4 bytes) | ciphertext (length bytes) | GCM tag (16 bytes)
Final record: length 0 (4 bytes) | authenticated empty-message tag (16 bytes)
```

For chunk index `i`, nonce = random prefix || `i` as an unsigned-width 32-bit counter. AAD = complete header || UTF-8 canonical UUID || index (4 bytes) || plaintext length (4 bytes). A **new content key is mandatory for every file**; code never rewrites ciphertext using an existing content key. Maximum chunk count is bounded below `Int.MAX_VALUE` to prohibit nonce wrap. All non-final data chunks are exactly 1 MiB. The catalog's authenticated plaintext size determines exact expected framing and file size.

Readers authenticate the final marker and framing on open; each requested data chunk is independently authenticated **before** returning any of that chunk's plaintext. Modified file headers, moved ciphertext between identities, reordered chunks, wrong keys, truncation and appended bytes fail authentication or framing. Entire-file verification happens on import. Random-access playback only authenticates requested chunks; corruption in an unvisited chunk is discovered when that chunk is read, not necessarily when opening a video.

## Import, crash consistency, deletion

1. Open the owner-selected system `content://` source. No full-file plaintext buffering.
2. Generate an independent key and write ciphertext to `<UUID>.partial`, while computing a source SHA-256 digest.
3. Flush/sync, reopen the encrypted file, authenticate every chunk, recompute the digest, and compare. Cancellation is checked while encrypting and verifying.
4. Rename to `<UUID>.cv`, sync the vault directory where the filesystem supports directory fsync, then atomically write the encrypted catalog. Only explicit unsupported-operation errors (`EINVAL`, `ENOSYS`, `EOPNOTSUPP`) are tolerated; other sync failures reject the import. Ciphertext contents are synced and fully verified in either case.
5. Report success only after catalog commit. Source files are never changed or deleted.

An empty encrypted catalog is committed on the first unlock, before any file import can begin. A crash before publication does not create a visible valid vault item. Incomplete `.partial` ciphertext is cleaned on a successful unlock. A crash between ciphertext finalization and catalog publication can leave an orphan `.cv` file; it is deliberately not guessed into the catalog or silently deleted. Its key may never have been persisted, so that **unreported import may be unrecoverable**. The source remains intact and should be imported again. Unlock reports orphaned and missing ciphertext counts without discarding indexed entries. This version has no orphan-recovery UI; orphan ciphertext can consume storage until app data is cleared. Never clear storage to reclaim it if other vault contents are needed.

A catalog failure does not trigger automatic deletion of finalized ciphertext because commit durability can be ambiguous. Files with a missing/corrupted catalog or missing Keystore key are retained; the app fails closed and does not generate replacement records over them. Data-loss warning messages never imply that ciphertext is recoverable without its key. Android `AtomicFile` plus filesystem synchronization reduces but cannot eliminate hardware/power-loss failures.

Delete first commits removal of the selected metadata/content keys, then unlinks **only** their UUID-matched files. If unlinks fail or the process stops between steps, inaccessible ciphertext can remain. Deletion is not a forensic secure-erase guarantee on flash storage, wear-levelled filesystems, RAM, or a privileged snapshot. There is no trash or undo. Deleting the last vault copy may permanently destroy access.

## Viewing and lifecycle

- No `FileProvider`, external export intents, plaintext preview files, shared-storage writes, or disk image cache.
- Images use bounded sampled decoding; visible thumbnails and viewers are held only in memory. Some formats/animated images are decoded as static frames.
- Video uses Media3 with a custom authenticated random-access source, with no HTTP stack or disk cache configured. On API 26 a generic video tile and duration replace thumbnails because bounded platform thumbnail decoding starts at API 27.
- PDFs use `StorageManager.openProxyFileDescriptor` and `PdfRenderer`. The descriptor is serviced from authenticated memory reads. It is not a filesystem plaintext copy. Unsupported/encrypted PDFs produce an error.
- Text decoding is limited to 1 MiB. Other files are encrypted and retained but no external opening/export exists in this version.
- Lock invalidates session generations, closes active readers, releases visible media players, removes catalog state, and clears the keypad. Readers check validity both before and after decrypting a chunk. Background imports are cancelled by the same generation gate. Opening either system picker starts the configured lock timer, including translucent photo pickers that do not call Activity.onStop. Activity-owned result callbacks retain selections across concealment/locking and activity recreation; they do not depend on the vault composable remaining mounted. Pending selections are memory-only: after a process kill the user may need to reselect originals. Supported persistable read grants are released after successful import, discard, or orderly ViewModel destruction; abrupt process death can leave an unused grant until Android or the provider revokes it.
- The single-task activity prevents multiple independent catalog writers from being created through repeated external launcher intents. Every new process is locked. Grace periods use Android monotonic elapsed time. The activity conceals private content on pause and locks on stop immediately by default, or after the chosen timeout. Configuration changes retain the ViewModel session, not a disk-stored unlock token.
- `FLAG_SECURE` applies even to the calculator. It reduces screenshots, insecure displays and recent-task previews on compliant Android devices. It does not hide the installed app from device settings, bypass accessibility services, or defeat cameras/OEM bugs. Media playback state may reset after recreation; files are unaffected.
- Raw PINs are never persisted, logged or placed in saved-instance state. Normal calculator digits, including a PIN being entered for unlock, are visible immediately to preserve ordinary calculator behavior. Explicit setup/confirmation/change screens remain masked. Shoulder-surfing is therefore a risk during unlock; screenshot protection does not protect against cameras or observers.
- Managed strings, decoder buffers, graphics buffers and keys may remain in memory until reclaimed. Mutable PIN and plaintext byte buffers are cleared where practical, but a perfect memory-erasure claim would be false.

## Backup, privacy, recovery

The manifest disables backups, includes pre-Android-12 full-backup exclusions and Android-12+ cloud/device-transfer exclusions, and uses no-backup private storage. No network or general storage permissions. No accounts, analytics, advertisements, crash upload SDKs or notifications.

Uninstall, clear-data, loss of a Keystore entry, device migration without that entry, unrecoverable corruption, or loss of both PIN and enrolled biometric access can permanently lose access. The app cannot restore deleted originals. Keep independent copies in a separate trusted backup system. Original files, source-provider caches, and pre-existing public thumbnails remain outside vault protection. There is no built-in encrypted backup or owner export in version 1.

Report security issues privately to the repository owner, without uploading real personal files, PINs, passwords or signing keys to public issues. There has been no third-party security audit.
